## 1. Идея

Программа берёт экспорт тест-рана и по каждому упавшему кейсу готовит **предложение**: завести новый баг (с готовым черновиком), связать с существующим, вернуть QA-инженеру за недостающими данными или отметить проблему окружения. Человек принимает решение по каждому кейсу. Ничего не попадает в трекер без подтверждения.

Главное отличие от AS IS — **проверка полноты до заведения бага** (AS IS пропускал TC-1150 и получал возврат от разработчика).

## 2. Целевой процесс

| # | Шаг | Что меняем по сравнению с AS IS | Кто: человек / программа / ИИ | Вход → выход | Контроль / исключение |
|---|---|---|---|---|---|
| 1 | Завершить тест-ран | Правило: к Failed/Blocked всегда прикладывается лог или скриншот | Человек (QA-инженер) | Кейсы → ран со статусами | Нарушение правила ловит шаг 3 |
| 2 | Импорт упавших кейсов | Вместо ручного фильтра — разбор CSV | Программа | CSV рана → список Failed/Blocked | Нет обязательных колонок → остановка с понятной ошибкой |
| 3 | Проверка полноты | **Новый шаг** | Программа | Кейс + вложения → «полный» / список недостающего | Неполный → предложение «вернуть QA-инженеру», черновик не создаётся (TC-1150) |
| 4 | Маскирование логов | **Новый шаг** | Программа | Лог → лог без e-mail, токенов, номеров карт и телефонов | Маскирование до любой передачи в ИИ и в отчёты |
| 5 | Проверка окружения | Было «на глаз» в шаге 3 AS IS | Программа (правила); ИИ — после пилота | Маск. лог + факт → продукт / окружение | Окружение → предложение «Blocked — окружение», уведомить ответственного за стенд (TC-1201) |
| 6 | Поиск дублей | Было — поиск по ключевым словам вручную | Программа (сходство текстов); ИИ-сходство — после пилота | Кейс + открытые баги → кандидаты с оценкой | Оценка ≥ порога → предложение «дубль BUG-N» (TC-1107); решение за человеком |
| 7 | Черновик баг-репорта | Было — ручное заполнение полей | ИИ (LLM) или шаблон; при сбое ИИ — шаблон | Кейс + маск. лог → заголовок, шаги, ожидаемо/фактически, окружение, компонент, серьёзность (предложение) | Ответ ИИ проверяется по схеме; неверный ответ или тайм-аут → шаблонный черновик |
| 8 | Решение по кейсу | Было — решение по ходу оформления | **Человек** (QA-инженер) | Предложение → approve / edit / reject / дубль / вернуть | Без решения кейс не публикуется. Серьёзность утверждает человек |
| 9 | Публикация | Было — ручное создание задачи | Программа | Подтверждённые решения → задача или комментарий в трекере | v1: только файл «outbox» (без доступа к трекеру). Повторный запуск не создаёт дублей (ключ: кейс + сборка) |
| 10 | Сводка по рану | Было — вручную к концу дня | Программа | Итоги → summary.md | Сводка формируется сразу после анализа |
| 11 | Проверка и приоритизация | Без изменений, но репорты приходят полными | Человек (QA Lead) | Баги → Triaged | Неполные репорты должны стать редкостью — это метрика |
| 12 | Взять баг в работу | Без изменений | Человек (разработчик) | Баг → в работе / Need info | Доля Need info — главная метрика эффекта |

Сводно: программа — шаги 2–6, 9, 10; ИИ — шаг 7 (и далее 5–6); человек — шаги 1, 8, 11, 12.

## 4. Границы первой версии (MVP)

**Входит:** локальный запуск; вход — CSV рана и CSV открытых багов; проверка полноты; маскирование; правила окружения; поиск дублей по сходству текста; шаблонный черновик и подключаемый ИИ-черновик (локальная или внешняя LLM через совместимый API); решения через CLI; публикация в файл outbox; сводка.

**Не входит:** интеграция с системой управления тестами и реальная запись в трекер (только описание и заготовка с повторами); веб-интерфейс; обработка скриншотов и видео; автоматическое решение без человека; обучение модели.

## 5. Эффект и как его измерить

| Метрика | AS IS (демо-допущение) | Цель пилота | Как измеряем |
|---|---|---|---|
| Время QA на один упавший кейс | 15–20 мин | ≤ 7 мин (проверка + правка черновика) | Отметки времени: анализ → решение (decisions.json) + самоотчёт QA на 2 ранах |
| Доля репортов, возвращённых на уточнение (Need info) | ~25 % | ≤ 10 % | Статусы в трекере за 4 недели до и после |
| Доля дублей среди заведённых | ~10 % | ≤ 3 % | Закрытия с резолюцией Duplicate в трекере |
| Время от конца рана до сводки | к концу дня | ≤ 30 мин | Время файла summary.md относительно окончания рана |
| Точность предложений программы | — | ≥ 80 % совпадений с решением человека | decisions.json: доля approve без правок |

Расчёт экономии для бизнес-проверки — в разделе 9; пока это гипотеза: при 30 кейсах в неделю и сокращении с ~17 до ~7 мин освобождается ~5 ч QA в неделю.

## 6. Что изменилось относительно AS IS
