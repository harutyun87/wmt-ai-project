# Ревью кода bugdraft

## Когда применять

- Перед слиянием любой ветки или MR в `main`.
- После реализации задачи из `docs/TASKS.md` (раздел 6 паспорта).
- По запросу: «проверь diff», «сделай ревью MR !N».

Не применять для документов без кода — для них достаточно проверки по шапке артефакта.

## Входы

| Вход | Откуда | Обязателен |
|---|---|---|
| Diff | `git diff main...HEAD`, файл `.diff` или MR из GitLab (см. ниже) | Да |
| Версия | Хэш коммита или `diff_refs` MR — указывается в каждом замечании | Да |
| ТЗ | `docs/SPEC.md` (сценарии, ошибки, контракты, критерии приёмки) | Да |
| Тесты | `python -m unittest discover -s tests` | Да |

## Шаги

1. **Зафиксировать версию.** Записать хэш базы и головы. Без версии замечания не воспроизводимы.
2. **Прочитать diff целиком** и для каждого изменённого файла — окружающий код, а не только строки diff.
3. **Сопоставить с ТЗ.** Для каждого изменения найти, какой сценарий (S*), ошибку (E*) или критерий (AC*) оно затрагивает. Изменение, которое нарушает контракт из SPEC 6, — всегда замечание.
4. **Проверить обязательные свойства проекта** (нарушение — минимум High):
   - в LLM, отчёты и outbox попадает только маскированный текст (SPEC 2, AC6);
   - ничего не публикуется без решения человека (AC7);
   - повторная публикация не создаёт дублей (AC8);
   - секреты — только из переменных окружения;
   - файлы читаются и пишутся в UTF-8, вывод в консоль — UTF-8 (Windows).
5. **Запустить тесты** на голове diff. Упавший тест — доказательство. Если свойство не покрыто тестом — написать минимальный воспроизводящий тест или команду и приложить вывод.
6. **Отсеять предположения.** Замечание без условия сбоя и доказательства не публикуется; его можно записать как вопрос.
7. **Сформировать отчёт** в формате ниже, отсортировать по серьёзности.
8. **Публикация** — только по решению пользователя (см. GitLab).

## Формат замечания

| Поле | Содержание |
|---|---|
| Файл / строка / версия | `src/bugdraft/publish.py:71 @ 1a2b3c4` |
| Серьёзность | Blocker — нарушает обязательное свойство или ломает сценарий; High — неверный результат в реальном случае; Medium — граничный случай, деградация; Low — сопровождаемость |
| Условие сбоя | Конкретный вход или последовательность действий → неверный результат |
| Доказательство | Упавший тест, вывод команды или цитата строки с объяснением |
| Исправление | Что изменить; при возможности — фрагмент кода |

Итог отчёта: **Можно сливать / Можно после исправления Blocker и High / Нельзя сливать**.

## Ограничения

- Не исправлять код молча: ревью предлагает исправление, вносит его автор.
- Не оценивать стиль, если он не влияет на поведение (форматирование — Low или не писать).
- Не выдумывать сбои: нет доказательства — нет замечания.
- Не публиковать замечания в GitLab без явного решения пользователя.
- Не использовать и не показывать токены; токен GitLab — только из `GITLAB_TOKEN`.

## GitLab (подключение без публикации по умолчанию)

Получение MR и diff (только чтение, токен с правом `read_api`):

```bash
# версия: diff_refs.base_sha / head_sha
curl -s -H "PRIVATE-TOKEN: $GITLAB_TOKEN" "$GITLAB_URL/api/v4/projects/<id>/merge_requests/<iid>"
# изменения
curl -s -H "PRIVATE-TOKEN: $GITLAB_TOKEN" "$GITLAB_URL/api/v4/projects/<id>/merge_requests/<iid>/diffs"
# или локально
git fetch origin merge-requests/<iid>/head:mr-<iid> && git diff main...mr-<iid>
```

Запуск ревью: в CI — задача `review` на событие MR, артефакт `review-report.md`; локально — этот скилл по diff.

Публикация замечаний — **отдельный шаг** после решения пользователя, токен с правом `api`:

```bash
curl -s -X POST -H "PRIVATE-TOKEN: $GITLAB_TOKEN" \
  --data-urlencode "body@review-report.md" \
  "$GITLAB_URL/api/v4/projects/<id>/merge_requests/<iid>/notes"
```

Без доступа к GitLab скилл работает локально по `git diff` или файлу `.diff`.
