# Карточка процесса

> **Демо-процесс.** Процесс и все цифры — учебные допущения, а не данные реальной компании.
> Перед использованием в работе каждую цифру нужно заменить замером (см. QUESTIONS.md).

Статус: черновик
Дата: 2026-11-16

## 1. Процесс

- **Название:** Оформление баг-репортов по результатам ручного тестирования
- **Домен / подразделение:** QA, разработка ПО (демо-продукт — интернет-магазин «ShopDemo»)
- **Владелец процесса (роль):** QA Lead
- **Участники (роли):** QA-инженер (проводит тест-ран и заводит баги); QA Lead (проверяет качество репортов, приоритизирует); разработчик (получает баг, возвращает на уточнение); тимлид / PM (триаж, решает, что чинить в релизе)

## 2. Зачем бизнесу

- **Какую задачу решает процесс:** превращает упавшие тест-кейсы в баг-репорты, по которым разработчик может воспроизвести и исправить дефект без дополнительных вопросов.
- **Что будет, если его не выполнять или выполнять плохо:** дефекты уходят в релиз или чинятся с задержкой; разработчики тратят время на уточнения; дубли раздувают бэклог и искажают метрики качества.
- **Главная боль сейчас:** ручное оформление занимает много времени после каждого рана; репорты неполные (нет окружения, лога, шагов) — их возвращают на уточнение; дубли заводятся, потому что поиск по трекеру делается «на глаз».

## 3. Границы

- **Старт (что запускает процесс):** завершён тест-ран по сборке, в нём есть кейсы со статусом Failed или Blocked.
- **Вход:** экспорт тест-рана из системы управления тестами (CSV: кейс, шаги, ожидаемый и фактический результат, статус, сборка, окружение), логи и скриншоты к упавшим кейсам, список открытых багов в трекере.
- **Конечный результат («готово»):** по каждому упавшему кейсу — либо заведённый баг-репорт по шаблону и связанный с кейсом, либо отметка «дубль бага N» / «не баг (причина)»; QA Lead видит сводку по рану.
- **Что точно не входит:** исправление дефектов, ретест после исправления, автотесты, планирование тестирования.

## 4. Масштаб (оценки)

- **Частота / объём:** 3 тест-рана в неделю, ~120 кейсов в ране, ~8 % Failed/Blocked → ~10 упавших кейсов на ран, ~30 в неделю — _допущение (демо)_
- **Время на один случай:** 15–20 мин на баг-репорт (поиск дублей, воспроизведение, оформление, вложения) — _допущение (демо)_
- **Доля исключений / ошибок:** ~25 % репортов возвращают на уточнение; ~10 % — дубли; ~15 % упавших кейсов — не баг (окружение, тестовые данные, устаревший кейс) — _допущение (демо)_
- **Источник цифр:** допущение для учебного примера; замера нет

## 5. Системы и данные (обобщённо)

- **Системы:** система управления тест-кейсами (экспорт CSV); баг-трекер (Jira или GitLab Issues — уточнить); мессенджер команды для уведомлений
- **Чувствительные данные в процессе:** в реальной работе — да: скриншоты и логи могут содержать тестовые учётки, токены, данные клиентов со стенда. В учебном проекте — только синтетика.
- **Ограничения ИБ и доступов:** создание задач в трекере — только от имени сервисной учётки с минимальными правами и после подтверждения человеком; логи перед отправкой в LLM маскируются.

## 6. Гипотеза автоматизации

- **Что хочется автоматизировать в первую очередь:** черновик баг-репорта по упавшему кейсу (заголовок, шаги, ожидаемо/фактически, окружение, вложения) и поиск возможных дублей среди открытых багов.
- **Где может помочь ИИ, а где нужен человек:**
  - программа — разбор экспорта тест-рана, сбор логов и метаданных, создание задачи через API трекера;
  - ИИ — формулировка заголовка и шагов, предложение серьёзности, поиск похожих багов по смыслу, выделение строки ошибки из лога;
  - человек (QA-инженер) — проверяет черновик, подтверждает «баг / дубль / не баг», утверждает серьёзность; заведение в трекер — только после подтверждения.
- **Как поймём, что стало лучше:** время на один баг-репорт; доля возвратов на уточнение; доля дублей; время от падения кейса до заведения бага.

## 7. Синтетический пример

Подробные данные — в `data/synthetic/` (описание — в `data/synthetic/README.md`).

```
Вход:      кейс TC-1042 «Оплата картой: применение промокода» — Failed на сборке 2.14.0-rc3, Chrome 131 / stage;
           фактически: итог не пересчитан, в логе 500 от POST /api/cart/promo.
Действия:  поиск дублей среди открытых багов → совпадений нет → черновик репорта → проверка QA-инженером → заведение.
Результат: новый баг «Промокод не применяется к корзине: 500 на POST /api/cart/promo», Major, связан с TC-1042.
```
